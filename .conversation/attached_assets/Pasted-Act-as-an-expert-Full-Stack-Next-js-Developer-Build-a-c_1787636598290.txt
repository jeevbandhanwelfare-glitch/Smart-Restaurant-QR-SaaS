DATABASE SCHEMA — write as supabase/schema.sql, and this must be the FIRST file written
============================================================
1. profiles: id (uuid, FK to auth.users), full_name, role (enum: admin, kitchen, waiter, customer), created_at
2. restaurant_tables: id, table_number (unique int), qr_slug
3. menu_categories: id, name, sort_order
4. menu_items: id, category_id (FK), name, description, price, is_veg (boolean), is_available (boolean)
5. orders: id, table_number, customer_id (uuid, nullable FK to profiles), status (enum: placed, preparing, ready, served, completed, cancelled), estimated_minutes, accepted_at, notes, created_at, updated_at
6. order_items: id, order_id (FK), item_name, item_price, quantity, special_instructions, is_veg
7. waiter_calls: id, table_number, type (enum: waiter, water, bill), status (enum: pending, claimed, resolved), claimed_by (uuid FK to profiles), created_at, claimed_at, resolved_at
8. waiters: id (uuid, FK to profiles), status (enum: free, busy, offline), updated_at

Add all relevant tables to the supabase_realtime publication. Write RLS policies scoped by role via auth.uid() and a helper function that reads the caller's role from profiles:
- only role="admin" writes menu_items/menu_categories/restaurant_tables
- only role="kitchen"/"admin" updates orders.status
- only role="waiter"/"admin" updates waiter_calls/waiters
- anon (guest, no login) can still INSERT into orders/order_items/waiter_calls for guest ordering, and SELECT their own order by id — this is what makes the no-login customer flow work

1) "/" — THE CUSTOMER APP (default homepage, no login required)

2) /login — shared login/signup form
   - Primary flow: staff login (email + password).
   - Secondary, clearly optional flow: customer sign in / create account (always role="customer").
   - Redirect logic exactly as described in the CRITICAL ROUTING BEHAVIOR section above.

3) /kitchen (role: kitchen, admin) — Kitchen Display System
   - Dark dashboard, 3 columns: New / Preparing / Ready.
   - Realtime subscribed to INSERT on orders/order_items and UPDATE on orders — instant updates, zero refresh.
   - Order tickets: perforated top-edge card styling, items with quantity + special instructions, live elapsed timer.
   - "Accept & Set Time" button opens a modal for entering estimated prep minutes → sets status=preparing, accepted_at=now(), estimated_minutes.

   - "Start Shift" button that creates/resumes a Web Audio API AudioContext (unlocks audio from a real user gesture — do NOT use an mp3 file). Every new order arriving via the Realtime INSERT subscription must trigger a loud, continuously looping notification sound built purely with oscillator + gain nodes (a repeating multi-tone chime, ~1 second interval, similar to a food-delivery app ringtone). Track ringing orders in a set; the alarm for a given order loops until that order's "Accept & Set Time" is confirmed; the sound fully stops only once every ringing order has been acknowledged. Implement as lib/kitchenAlarm.ts with arm(), ring(orderId), and acknowledge(orderId) methods.

4) /waiter (role: waiter, admin) — mobile UI for floor staff
   - Large Free (green) / Busy (red) toggle tied to the logged-in waiter's own waiters row.
   - Live pending waiter_calls list via Realtime, shown to free waiters.
   - "Accept" claims a call via a conditional UPDATE (`.eq('id', callId).eq('status', 'pending')`) so only the first click wins; the losing waiter's ping disappears automatically once their Realtime subscription confirms someone else claimed it.
   - On successful claim: that waiter's own status flips to Busy, the task appears in "My Tasks", and the customer sees "Waiter is on the way" live.
   - "Resolved" button on a claimed task sets it resolved and flips the waiter back to Free.

5) /admin (role: admin) — management dashboard (do not skip this — it must exist and be reachable via /login)
   - Overview: live counts of active orders, pending calls, free/busy waiters.
   - Menu management: full CRUD for menu_categories and menu_items (name, price, veg/non-veg, availability toggle).
   - Table management: full CRUD for restaurant_tables, plus a screen to view/print each table's QR code (encoding a URL like https://yourapp.com/?table=N — generate client-side with a QR code library).
   - Staff management: "Add Staff" form (creates kitchen/waiter accounts as described in the Auth section), and a list of all staff with their current live status.
   - Orders log: a searchable/filterable table of all past orders.
